# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

A flat collection of standalone **Pine Script** (TradingView) indicators and strategies for trading ES/NQ futures, SPX/SPY options, and gold, plus the PNG chart screenshots referenced from `README.md`. There is no build system, package manager, linter, or test suite — these `.txt` files are pasted directly into TradingView's Pine Editor and run there. `README.md` is the canonical index: it explains what each script does, which ticker/timeframe it targets, and links each script to its chart screenshot.

## Repository layout

- Everything lives at the repo root — no subdirectories. Scripts are plain-text Pine Script saved as `.txt` (a few, like `es-futures`, `nq-future`, `futures-2024`, `price_action`, `ai-prediction`, have no extension but are also Pine Script).
- `*.png` files are TradingView chart screenshots, embedded in `README.md` via raw GitHub URLs (`.../raw/main/<file>.png?raw=true`). They are documentation artifacts, not generated by any script in this repo.
- `README.md` doubles as changelog and shop-front: each section names a script file, states its ticker/timeframe, sometimes an accuracy claim, a Patreon link, and a linked screenshot.

## "Commands"

There is nothing to install, build, lint, or test. The only way to "run" a script is to paste it into TradingView's Pine Editor (Chart → Pine Editor → paste → "Add to chart"). When changing a script, sanity-check it the way a human would:

- Confirm the `//@version=N` pragma at the top matches the syntax used (v4/v5/v6 differ — see Conventions below); mixing eras of syntax in one file is the most common break.
- Read through for balanced `if`/indentation blocks — Pine Script is whitespace-sensitive like Python.
- If you touch a `request.security()` call or anything gated by `barstate.isconfirmed`, re-check the repaint-safety notes for that file (many files' headers document exactly what was changed and why — follow the same pattern for new edits).
- There's no automated way to verify correctness in this repo; note in your summary that changes are untested until pasted into TradingView.

## Conventions specific to this codebase

**Version pragma**: every script starts with `//@version=4|5|6` (mostly v5; newest scripts use v6, e.g. `es-futures-no-repaint-v1.6.txt`/`v1.7.txt`, `spx-30m.txt`, `best-chart.txt`). Match the existing pragma of the file you're editing — v4/v5/v6 have real syntax differences (e.g. `study()` vs `indicator()`, `security()` vs `request.security()`).

**License/attribution header**: most files open with:
```
// This source code is subject to the terms of the Mozilla Public License 2.0 at https://mozilla.org/MPL/2.0/
// © <author handle, e.g. binancash / donaldit / donaldit.net>
```
Preserve this header when editing an existing file; don't strip attribution.

**`indicator()` vs `strategy()`**: `indicator()` scripts only plot/alert (no simulated P&L); `strategy()` scripts add backtestable entries/exits (`strategy.entry`, `strategy.exit`, `strategy.close`) and show the Strategy Tester results panel. Check which declaration a file uses before assuming `strategy.*` calls are available.

**Repaint safety** (actively maintained in the `es-futures-no-repaint-v1.*.txt` series, and referenced throughout README): a strategy "repaints" when it uses information not yet available at the time a live signal fires, making backtests look better than live trading. The fixes applied across v1.0→v1.7 establish the pattern to follow:
- Always pass `lookahead = barmerge.lookahead_off` to `request.security()` (never `lookahead_on`).
- Multi-timeframe values (HTF averages, etc.) must reference confirmed bars only — avoid `[0]` (current, still-forming bar) on security-fetched series.
- Persistent state (`var bool`/`var float` cross/latch flags) should only update when `barstate.isconfirmed` is true.
- When you fix a repaint bug, add a short changelog comment block at the top of the file (see below) explaining what changed and why, mirroring the existing `v1.x CHANGELOG` blocks.

**In-file changelogs**: several actively-iterated scripts embed their version history directly in a header comment block, e.g. `es-futures-no-repaint-v1.7.txt`:
```
// ============================================================
// v1.7 CHANGELOG (vs v1.6)
//  FIX  ...
//  NEW  ...
//  PRUNE removed dead code: ...
// ============================================================
```
When you meaningfully change one of these versioned files, either bump to a new `vX.Y` filename (matching the existing `es-futures-no-repaint-v1.0.txt` … `v1.7.txt` sequence) and add a changelog block, or add a dated note in `README.md` — follow whichever pattern the file family already uses rather than inventing a new one.

**Webhook auto-trading via `alertcondition()`**: several strategies emit JSON alert payloads consumed by a companion bot (see `es-futures-no-repaint-v1.7.txt` tail):
```pine
alertcondition(longCondition and not lock_time and allowLong, title = 'V1.7 BUY Signal',
  message = '{"action":"buy","symbol":"{{ticker}}","qty":1,"price":{{close}},"tf":"1m"}')
```
These messages are posted by TradingView alerts to a webhook and picked up by the separate [tradovate-trading-bot](https://github.com/dearvn/tradovate-trading-bot) repo (Tradovate WebSocket/REST). If you add new entry/exit conditions to a strategy that already wires up alerts, keep the JSON `action` vocabulary (`buy`/`sell`/`closeLong`/`closeShort`) and placeholder usage (`{{ticker}}`, `{{close}}`) consistent with the existing alerts in that file.

**No single "current" script** — the repo is an accumulation of experiments and iterations, not a curated library. `README.md`'s "IMPORTANT" section calls out `trade-futures.txt` as the one actually in live use as of the last update, with per-ticker input values (`ES: input IN = 5, input OUT = 3`; `NQ: input IN = 15, input OUT = 12`). Many other files (`ES1M-BEST.txt`, `best-indicator.txt`, `win-99.txt`, `swing.txt`, etc.) are prior/parallel variants referenced by name in README for specific market conditions (weak market, market crash, manual trading). When asked to "fix the trading script" without a filename, check `README.md` first to identify which file is meant.

**External Pine Script libraries**: at least one file imports a third-party TradingView library (`price_action` imports `jdehorty/KernelFunctions/2 as kernels`). These imports only resolve inside TradingView's Pine Editor, not locally — don't try to "install" them.

## Updating README.md

Because README.md is the index and user-facing documentation for this repo, any new script or meaningfully-changed script should get a corresponding entry: file name, ticker/timeframe, and (if there's a screenshot) an `![Alt text](.../raw/main/<file>.png?raw=true "...")` embed following the existing pattern. Keep new sections consistent with the informal changelog style already used (most-recent updates tend to be added near the top or in a dedicated section, not necessarily strictly chronological).
